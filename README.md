## 1. Введение

Тема моего проекта "Разработка и обучение нейросети под задачи машинного обучения для запуска на мобильных устройствах".

Я выбрал эту тему потому что сам когда-то столкнулся с отсутствием хорошего бесплатного переводчика, который можно было бы использовать как в своих проектах для массового перевода, так и для личного использования, и мне показалось что такой переводчик может понадобиться не только мне.

Продуктом проекта будет готовая модель нейросети для перевода с русского на английский, а так же репозиторий с открытой лицензией, содержащий весь исходный код проекта, чтобы любой желающий мог воспроизвести переводчик для любой пары языков или модифицировать проект под свои нужды.

---

## 2. Постановка задачи

### 2.1 Формализация

Главной задачей проекта являлось разработка и обучение такой модели нейросети для перевода с одного языка на другой, которая сочетала бы в себе компактность для возможности запуска на устройствах с минимальными вычислительными мощностями и качество перевода чтобы при использовании модели сохранялся смысл текста.

### 2.2 Выбор языков

Для демонстрации возможностей своего проекта я выбрал именно перевод с русского на английский чтобы иметь возможность контролировать качество получаемого перевода, ведь я знаю именно русский и английский языки.

### 2.3 Требования

Чтобы моей моделью мог воспользоваться практически каждый мне пришлось ставить очень жёсткие требования по количеству ресурсов для работы с моделью, а значит и по её размерам. Проведя небольшой опрос в своём кругу общения я понял что большое количество людей всё ещё ходит с телефонами с тремя гигабайтами оперативной памяти, это я и взял за планку. Очевидно, модель не может занимать все три гигабайта, поскольку на телефоне кроме неё будут работать другие приложения и операционная система, поэтому за ограничение я взял полтора гигабайта. По качеству перевода мне не удалось сформулировать чётких требований, поэтому в данном аспекте я сравнил свой переводчик с IT гигантами в данной сфере, вроде Яндекс, Google и DeepL.

## 3. Программные решения

### 3.1 Архитектура

В начале проекта небыло понимания того, какие инструменты использовать, поэтому я начинал с простейшего - обычной полносвязной нейросети, персептрона, однако я быстро понял что эта архитектура плохо подходит под эту задачу, поэтому я стал пробовать другие архитектуры и в конце-концов я пришёл к трансформерам. Моя реализация чем-то похожа на моего не очень удачного вдохновителя - семейство моделей от google "google-T5", но имеет некоторые модификации: ReLU заменён на более современный GeLU, сильно модифицирован механизм позиционного кодирования, а так же оптимизирован механизм внимания. То есть это всё ещё стандартный трансформер со стандартным механизмом кодирования (так как пока что модель заточена именно под относительно короткие тексты, его модификации скорее всего только мешали бы) и обычным многоголовым механизмом внимания.

### 3.2 Обучение

Когда я только начинал проект, мне показалось странным что разработчики обучают свои модели переводу сразу множества языков, хотя заметная их часть всё равно обрабатывается некорректно, поэтому за парадигму я взял "одни веса - одна языковая пара", так модель не будет рассеивать свою обобщающую способность на десяток языков с акцентом всего на несколько из них, а будет знать только два языка, но хорошо.

### 3.3 Оценка качества

Сначала оценка качества казалась мне самым простым аспектом, но я сильно ошибся - она оказалась одним из самых сложных. В идеальных условиях для оценки качества, особенно при обучении нужны люди, знающие оба языка, но это слишком ресурсозатратно, поэтому пришлось прибегать к иным методам. Изначально я планировал обучение модели по принципу GAN - обучать параллельно две модели: одну для перевода, а другую для оценки "человечности" перевода, точнее его близость по смыслу к оригиналу, но этот метод при дальнейшем изучении оказался неэффективным и слабоприменимым к области обработки естественных языков. Поэтому я перешёл к способу более популярному - при обучении считать за ошибку то, насколько ожидаемый следующий фрагмент текста модель посчитала вероятным для использования, а при использовании отталкивать от своих оценок и от схожести с переводами переводчиков от IT гигантов.

### 3.4 Данные для обучения

Во время работы использовались следующие наборы данных:

| Набор данных                     | Примечание                                                     |
| -------------------------------- | -------------------------------------------------------------- |
| `wmt/wmt19`                      | —                                                              |
| `ymoslem/Tatoeba-Translations`   | —                                                              |
| `HuggingFaceFW/finetranslations` | Не использовался при обучении итоговой модели                  |
| `openlanguagedata/flores_plus`   | Был использован только для валидации, в обучении не участвовал |

Перед использованием содержимое наборы данных были отфильтрованы по длине и токенизированы. Иных изменений не вносилось.

## 4. Использование материалов проекта

### 4.1 Обучение токенизатора

Для обучения токенизатора следует запустить файл `tok_learn.py`, в результате выполнения появится директория `tokenizer/` с файлами токенизатора.

```bash
python tok_learn.py
```

### 4.2 Предобработка наборов данных

Для предварительной обработки данных следует запустить файл `pre_tokenize.py`, для запуска требуется обученный токенизатор (см. [п. 4.1](#41-обучение-токенизатора)), его главную директорию следует поместить в одну директорию с программой, в результате появится директория `sources/` с двумя вложенными директориями: `s512_full/`, `s512_val/`. В них будут находиться файлы сохранений обработанных тренировочного и валидационного датасетов соответственно.

```bash
python pre_tokenize.py
```

> **ВНИМАНИЕ!** Временные файлы, создаваемые данной программой могут занимать большое количество постоянной памяти.

### 4.3 Обучение модели переводчика

Для обучения переводчика следует запустить файл `train.py`, для запуска понадобятся тренировочный и валидационный наборы данных (см. [п. 4.2](#42-предобработка-наборов-данных)), а так же файл с имплементацией модели `imp.py` и конфигурационный файл `train_config.txt`. Директории наборов данных могут быть произвольны, но требуют указания путей в конфигурационном файле, имплементация и конфигурационный файл должны быть в одной директории с программой. В результате выполнения программы в директории для сохранения контрольных точек появятся контрольные точки с обученными весами, их файлы будут иметь расширение `.pt`.

```bash
python train.py
```

### 4.4 Тестирование обученных весов

Для тестирования обученных весов следует запустить файл `use.py`, для запуска потребуются обученные веса из сохранённой контрольной точки (см. [п. 4.3](#43-обучение-модели-переводчика)), обученный токенизатор (см. [п. 4.1](#41-обучение-токенизатора)), его главную директорию следует поместить в одну директорию с программой, а так же файл с имплементацией модели `imp.py`. Файл с сохранением контрольной точки следует переименовать в `transformer.pt` и поместить в одну директорию с программой, файл `imp.py` так же следует поместить в эту директорию. Программа через консольный интерфейс принимает на вход текст для перевода и выдаёт дешифрованные в текст предсказания модели из контрольной точки.

```bash
python use.py
```

### 4.5 Преобразование файла сохранения в готовую модель

Для преобразования контрольной точки в модель, готовую для повседневного использования и распространения следует запустить файл `onnx_export.py`, для запуска потребуется контрольная точка с обученными весами (см. [п. 4.3](#43-обучение-модели-переводчика)), её файл следует переименовать в `transformer.pt` и поместить в директорию с программой. В результате выполнения программы появится директория `onnx_export/`, в которой будет содержаться четыре файла:

```bash
python onnx_export.py
```

| Файл | Описание |
|---|---|
| `encoder_fp32.onnx` | Стандартная точность (FP32) |
| `decoder_fp32.onnx` | Стандартная точность (FP32) |
| `encoder_fp8.onnx` | Повышенная степень сжатия (FP8) |
| `decoder_fp8.onnx` | Повышенная степень сжатия (FP8) |

Файлы `encoder_fp32.onnx` и `decoder_fp32.onnx` эквивалентны `encoder_fp8.onnx` и `decoder_fp8.onnx` соответственно. Вторые имеют бо́льшую степень сжатия, а значит при использовании модель будет потреблять меньше ресурсов компьютера, но может в некоторой степени потерять в точности своих предсказаний (в реальности в конкретном случае этого не наблюдается). Каждая из пар файлов представляет собой одну модель.

### 4.6 Использование готовой модели

Использовать готовую модель можно где угодно, для демонстрации подготовлено несколько программ, готовых для использования:

| Файл | Интерфейс | Примечание |
|---|---|---|
| `web.py` | Веб-сайт | — |
| `telegram.py` | Telegram-бот | Для работы дополнительно требует токен API Телеграмма для бота |
| `onnx_use.py` | Консоль | В процессе разработки |

Каждая из этих программ для работы требует обученный токенизатор (см. [п. 4.1](#41-обучение-токенизатора)) и готовую модель (см. [п. 4.5](#45-преобразование-файла-сохранения-в-готовую-модель)). Главную директорию токенизатора следует поместить в одну директорию с соответствующей программой. Файлы готовой модели следует переименовать, убрав всё от нижней черты (включительно) до точки, отделяющей расширение файла, например:

```
encoder_fp32.onnx  →  encoder.onnx
decoder_fp8.onnx   →  decoder.onnx
```

При запуске программы можно пользоваться переводчиком через соответствующий интерфейс: веб-сайт для `web.py`, телеграмм чат с ботом для `telegram.py`, консольный интерфейс для `onnx_use.py`.

## 5. Выводы

В ходе проекта была разработана и обучена компактная нейросеть для машинного перевода с русского языка на английский, ориентированная на запуск в условиях ограниченных вычислительных ресурсов.

| Поставленная задача                   | Результат                                                                                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Размер модели не более 1,5 ГБ         | Выполнено: модель в формате FP8 укладывается в ограничение: меньшая модель весит примерно 690 мегабайт, а средняя 950 мегабайт.           |
| Сохранение смысла перевода            | Выполнено: модель корректно перевела все тестовые запросы.                                                                                |
| Сравнимость с коммерческими сервисами | Частично выполнено: хотя модель неплохо показала себя при использовании, она всё ещё уступает по качеству перевода коммерческим сервисам. |
| Открытый исходный код                 | Выполнено: репозиторий опубликован на сайте площадке [Github](https://github.com/cesslav/polyglot) под открытой лицензией AGPLv3                                                                                   |

Принятая парадигма "одни веса - одна языковая пара" доказала свою эффективность: специализированная модель стабильно превосходит универсальные многоязычные аналоги сопоставимого размера на целевой языковой паре.

Квантование до FP8 позволило сократить объём занимаемой памяти без заметных потерь в точности предсказаний, что подтверждает пригодность подхода для развёртывания на мобильных устройствах.

Таким образом, все ключевые цели проекта достигнуты: создана работоспособная, открытая и воспроизводимая система машинного перевода, доступная как конечным пользователям, так и разработчикам.

## 6. Направления дальнейшего развития проекта

### 6.1 Поддержка новых языковых пар

На данный момент обученая только для перевода c русского на английский, однако планируется реализация модульности, то есть поддержка совместимости энкодеров и декодеров разных языковых пар между собой. Например заранее обучается две модели: русский-английский и французский-немецкий, а из их частей можно будет составить модели для перевода с русского на немецкий и с французского на английский.

### 6.2 Улучшение качества перевода

Несмотря на удовлетворительные результаты, есть ряд направлений для повышения качества:
- Фильтрация имеющихся наборов данных по качеству перевода;
- тонкая настройка (fine-tuning) на специализированных доменах — юридическом, медицинском, техническом и пр.;
- обучение с подкреплением на основе человеческой обратной связи (RLHF) для улучшения "человечности" переводов;
- расширение тренировочного корпуса за счёт дополнительных открытых параллельных датасетов.

### 6.3 Развитие пользовательских интерфейсов

- публикация полноценного Python-модуля для лёгкой интеграции моделей в сторонние проекты как библиотеки;
- реализация REST API-сервера для общего встраивания переводчика в веб-приложения и сервисы.
