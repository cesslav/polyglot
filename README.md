## 1. Введение

Тема этого проекта - «Разработка инструментария для обучения нейросети под задачи машинного перевода для запуска на мобильных устройствах», рабочее название проекта - "Полиглот".

Актуальность проекта обусловлена отсутствием доступного инструментария для создания систем машинного перевода, пригодных как для массовой обработки текстов в рамках как сторонних разработок, так индивидуального использования.

Продуктами проекта являются готовая модель нейросети для перевода с русского языка на английский, приложение для запуска модели без доступа к интернету, а также репозиторий с открытой лицензией, содержащий полный исходный код проекта. Репозиторий предоставляет возможность любому пользователю воспроизвести переводчик для произвольной языковой пары или адаптировать проект под собственные нужды.

---

## 2. Постановка задачи

### 2.1 Формализация

Задачей проекта являлась разработка и обучение модели нейросети для перевода с одного естественного языка на другой, сочетающей компактность, достаточную для запуска на устройствах с минимальными вычислительными ресурсами, и качество перевода, обеспечивающее сохранение смысла исходного текста, а так же разработка полностью открытого инструментария для воспроизведения каждого шага - от реализации архитектуры нейросети до приложения для использования конечным потребителем. 

---

### 2.2 Выбор языков

В качестве демонстрационной языковой пары выбран перевод с русского языка на английский. Данный выбор обусловлен возможностью непосредственного контроля качества получаемых переводов.

---

### 2.3 Требования

С целью обеспечения широкой доступности модели были установлены жёсткие ограничения на потребление вычислительных ресурсов и, соответственно, на размер модели. По результатам исследования установлено, что значительная часть пользователей эксплуатирует устройства с тремя гигабайтами оперативной памяти. Данный показатель принят за ориентир. Поскольку часть ресурсов устройства занята операционной системой и иными приложениями, предельный объём памяти, занимаемой моделью, установлен в 1,5 гигабайта. Ввиду сложности формализации требований к качеству перевода проводилось сравнение разработанного переводчика с решениями ведущих участников рынка: Яндекс, Google и DeepL.

## 3. Программные решения

### 3.1 Архитектура

На начальном этапе проекта в качестве базовой архитектуры рассматривалась полносвязная нейросеть (перцептрон), однако данный подход был признан неэффективным для решения поставленной задачи. По результатам исследования альтернативных архитектур была выбрана архитектура трансформера. Реализованная модель основывается на оригинальной архитектуре трансформер, однако включает ряд модификаций: функция активации ReLU заменена на SwiGLU, механизм позиционного кодирования существенно переработан, механизм внимания оптимизирован. В остальном модель представляет собой стандартный трансформер со стандартным многоголовым механизмом внимания.  

---

### 3.2 Токенизатор

С самого начала было принято решение использовать собственный токенизатор. На данный момент используется unigram токенизатор, сделанный на основе библиотеки `tokenizers` и датасета `HuggingFaceFW/finetranslations` . Так как нет необходимости токенизировать большое количество языков, словарь токенизатора получилось значительно уменьшить относительно других нейростей-переводчиков, что, в свою очередь, позволило уменьшить размер модели. В дальнейшем, вероятно, придётся отказаться от этого решения.

---

### 3.3 Обучение

В качестве парадигмы принят подход «одни веса - одна языковая пара». Данное решение принято с целью устранения недостатков многоязычных моделей, обобщающая способность которых распределяется между множеством языков, что снижает качество обработки каждого из них. Специализированная модель, ориентированная на одну языковую пару, обеспечивает более высокое качество перевода в рамках этой пары при прочих равных. Обучение ведётся в обоих направлениях за один проход по батчу: функция потерь формируется как сумма потерь для пары src->tgt и tgt->src, что вдвое увеличивает эффективный объём обучающих данных без дополнительных затрат на их подготовку.  

---

### 3.4 Оценка качества

Оценка качества перевода является одним из наиболее сложных аспектов проекта. В идеальных условиях она предполагает привлечение экспертов, владеющих обоими языками, однако данный подход сопряжён со значительными ресурсными затратами. Первоначально рассматривалась возможность обучения по принципу GAN - с параллельным обучением двух моделей: одной для перевода и другой для оценки близости перевода к оригиналу по смыслу. Данный метод был отклонён как малоэффективный применительно к обработке естественных языков. В итоге принят более распространённый подход: на этапе обучения в качестве функции потерь используется вероятность, которую модель присваивает ожидаемому следующему фрагменту текста; при ручной оценке результатов обучения принимаются во внимание предсказания модели, субъективное мнение тестеров, а также близость предсказаний к переводам коммерческих сервисов.  

---

### 3.5 Хранение модели

В качестве формата хранения готовой модели выбран ONNX (Open Neural Network Exchange) - открытый стандарт представления моделей машинного обучения, разработанный с целью обеспечения их совместимости между различными фреймворками и платформами. Данный формат поддерживается широким спектром аппаратных ускорителей и сред выполнения. Модель разделена на два независимых файла — энкодер и декодер, — что позволяет кешировать результат работы энкодера при многократном декодировании одного и того же входного текста и упрощает замену отдельных компонентов без переобучения модели целиком.
Для дополнительного сокращения объёма занимаемой памяти применяется квантование весов полносвязных слоёв до точности INT8. Веса матриц механизма внимания при этом намеренно сохраняются в исходной точности FP32, поскольку они наиболее чувствительны к потере точности. Такой избирательный подход позволил существенно уменьшить размер модели без заметного снижения качества перевода.

## 4. Использование материалов проекта

### 4.1 Зависимости

Для работы с проектом необходим Python 3.10 или новее. Установите зависимости:

```bash
pip install torch einops transformers datasets tokenizers \
            onnx onnxruntime fastapi uvicorn flask \
            aiogram PyQt5
```

или

```bash
pip install -r requirements.txt
```

> **Примечание.** Для квантования в INT8 (`onnx_export.py`) требуется `onnxruntime >= 1.16`. Для обучения на GPU рекомендуется PyTorch с поддержкой CUDA или ROCm.

---

### 4.2 Обучение токенизатора 

Для обучения токенизатора необходимо запустить файл `tok_learn.py`. В процессе выполнения будет создана директория `tokenizer/` с файлами токенизатора.

```bash
python tok_learn.py
```

---

### 4.3 Предобработка наборов данных

Для предварительной обработки данных необходимо запустить файл `pre_tokenize.py`. Для запуска требуется обученный токенизатор (см. [п. 4.2](#42-обучение-токенизатора)); его главную директорию следует поместить в одну директорию с программой. В результате выполнения будет создана директория `sources/` с двумя вложенными директориями: `s512_full/` и `s512_val/`, содержащими файлы сохранений обработанных тренировочного и валидационного датасетов соответственно.

```bash
python pre_tokenize.py
```

> **ВНИМАНИЕ!** Временные файлы, создаваемые данной программой, могут занимать значительный дискового пространства.

---

### 4.4 Обучение модели переводчика

Для обучения переводчика необходимо запустить файл `train.py` или `train_ddp.py` для обучения на кластере из нескольких CPU/GPU/NPU/TPU. Для запуска требуются тренировочный и валидационный наборы данных (см. [п. 4.3](#43-предобработка-наборов-данных)), файл с реализацией модели `imp.py`, а также конфигурационный файл `train_config.json`. Директории наборов данных могут располагаться произвольно при условии указания соответствующих путей в конфигурационном файле; файлы с реализацией и с конфигурацией должны находиться в одной директории с программой. В процессе выполнения в директории для сохранения контрольных точек будут созданы файлы контрольных точек с обученными весами (расширение `.pt`).  

Конфигурационный файл `train_config.json` читается построчно в следующем порядке:
Параметры в конфигурационном файле `train_config.json`:

| №  | Параметр         | Описание                                                                                                                                                                                                                            |
|----|------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1  | `continue`       | `0` - начать обучение с нуля, `1` - продолжить с контрольной точки.                                                                                                                                                                 |
| 2  | `save_dir`       | Директория для сохранения контрольных точек. При продолжении обучения контрольная точка должна лежать в этой же директориии.                                                                                                        |
| 3  | `checkpoint`     | Размер батча. Имя файла контрольной точки (например, `transformer_epoch_5.pt`). Игнорируется при `is_continue=0`.                                                                                                                   |
| 4  | `batch_size`     | Следует указывать список из одного числа для обучения на одном устройстве или при одинаковом размере батча на всех устройствах батча, в иных случаях список должен содержать размер батча для каждого устройства. По умолчанию `1`. |
| 5  | `max_epochs`     | Максимальное число эпох. По умолчанию `200`.                                                                                                                                                                                        |
| 6  | `init_lr`        | Начальный шаг обучения. Игнорируется при `is_continue=1`. По умолчанию `0.001`.                                                                                                                                                     |
| 7  | `lr_decay`       | Коэффициент послойного затухания шага обучения. `1.0` - отключить. Игнорируется при `is_continue=1`. По умолчанию `0.9`.                                                                                                            |
| 8  | `d_model`        | Размерность эмбеддинга модели. По умолчанию `256`.                                                                                                                                                                                  |
| 9  | `vocab_size`     | Размер словаря. Должен совпадать с размером обученного токенизатора. По умолчанию `48000`.                                                                                                                                          |
| 10 | `num_layers`     | Количество слоёв энкодера. По умолчанию `4`.                                                                                                                                                                                        |
| 11 | `dec_depth_diff` | Разница в количестве слоёв между декодером и энкодером. По умолчанию `0`.                                                                                                                                                           |
| 12 | `dim_head`       | Размерность одной головы внимания. По умолчанию `64`.                                                                                                                                                                               |
| 13 | `num_heads`      | Число голов внимания. `0` - вычислить автоматически как `d_model // dim_head`. По умолчанию `0`.                                                                                                                                    |
| 14 | `mlp_mult`       | Множитель размера полносвязного слоя. По умолчанию `4`.                                                                                                                                                                             |
| 15 | `dropout`        | Вероятность отключения нейронов при обучении. `0` - отключить. По умолчанию `0`.                                                                                                                                                    |
| 16 | `train_ds_dir`   | Путь к тренировочному датасету (директория `s512_full`).                                                                                                                                                                            |
| 17 | `val_ds_dir`     | Путь к валидационному датасету (директория `s512_val`).                                                                                                                                                                             |

> Строки 6–15 считываются только при `continue=true`; при продолжении обучения конфигурация модели и оптимизатора восстанавливается из контрольной точки автоматически. Строки, начинающиеся с `#`, игнорируются. Контрольные точки сохраняются автоматически раз в час и по завершении каждой эпохи.

---

```bash
python train.py
```

### 4.5 Тестирование обученных весов

Для тестирования обученных весов необходимо запустить файл `raw_use.py`. Для запуска требуются обученные веса из сохранённой контрольной точки (см. [п. 4.4](#44-обучение-модели-переводчика)), обученный токенизатор (см. [п. 4.2](#42-обучение-токенизатора)) и файл с реализацией модели `imp.py`. Перед запуском необходимо указать в начале файла путь к директории с контрольной точкой и имя её файла:

```python
checkpoint_dir  = "./"
checkpoint_name = "transformer_epoch_1.pt"
device          = "cpu"   # "cuda" для GPU
```

---

Программа принимает текст для перевода через консольный интерфейс и выводит предсказания модели, декодированные в текст. Для выхода используйте `Ctrl+C`.

```bash
python raw_use.py
```

### 4.6 Преобразование файла сохранения в готовую модель

Для преобразования контрольной точки в модель, готовую к повседневному использованию и распространению, необходимо запустить файл `onnx_export.py`. Для запуска требуется контрольная точка с обученными весами (см. [п. 4.4](#44-обучение-модели-переводчика)). Перед запуском необходимо указать в конце файла путь к контрольной точке и директорию для сохранения результата:

```python
save_dir   = "onnx_export"
checkpoint = "./transformer.pt"
```

---

В результате выполнения будет создана директория `onnx_export/`, содержащая четыре файла:

| Файл                | Описание                        |
|---------------------| ------------------------------- |
| `encoder_fp32.onnx` | Стандартная точность (FP32)     |
| `decoder_fp32.onnx` | Стандартная точность (FP32)     |
| `encoder_int8.onnx` | Повышенная степень сжатия (INT8) |
| `decoder_int8.onnx` | Повышенная степень сжатия (INT8) |

---

Файлы `encoder_fp32.onnx` и `decoder_fp32.onnx` являются функциональными эквивалентами файлов `encoder_int8.onnx` и `decoder_int8.onnx` соответственно. Файлы в формате INT8 обеспечивают более высокую степень сжатия, что снижает потребление ресурсов устройства при работе модели; при этом возможно незначительное снижение точности предсказаний (в рамках обученных мной моделей данный эффект не проявился). Каждая из пар файлов представляет собой одну модель.

```bash
python onnx_export.py
```

Так же распространяется через Github ([https://github.com/cesslav/Polyglot_Mobile](https://github.com/cesslav/Polyglot_Mobile)) |
| `model_dist_server.py` | REST API                   | Сервер раздачи моделей для мобильного приложения.                                                                                                                                                                                                    |
| `desktop_app.py`       | Десктопное приложение      | Аналог приложения для запуска моделей на стационарных ПК и ноутбуках.                                                                                                                                                                                |

Каждая из перечисленных программ требует наличия готовой модели (см. [п. 4.6](#46-преобразование-файла-сохранения-в-готовую-модель)). Файлы модели необходимо переименовать, удалив суффикс после нижней черты (включительно) вплоть до расширения файла, например:

```
encoder_fp32.onnx  ->  encoder.onnx
decoder_int8.onnx  ->  decoder.onnx
```

---

Токенизатор должен находиться в поддиректории `tokenizer/` рядом с файлами модели. Итоговая структура директории модели:

```
<model_dir>
├── encoder.onnx
├── decoder.onnx
├── model_config.json
└── tokenizer/
    ├── tokenizer.json
    └── tokenizer_config.json
```

---

**`web.py`** - веб-интерфейс на базе Flask. Модели загружаются из поддиректорий директории, заданной переменной среды `MODELS_DIR` (по умолчанию `./onnx_export/for_web`). После запуска интерфейс доступен по адресу `http://localhost:9090`(пример можно посмотреть, перейдя по ссылке [http://igorpet.ru:9090](http://igorpet.ru:9090)).

```bash
python web.py
```

---

**`telegam.py`** - Telegram-бот на базе библиотеки aiogram. Переводит любое входящее сообщение и возвращает результат в чат. Перед запуском необходимо указать в файле пути к модели и токенизатору. При запуске программа запросит токен API бота в интерактивном режиме.

```bash
python telegram.py
```

---

**`onnx_use.py`** - консольный переводчик с поддержкой AMD GPU через провайдер MIGraphX. Перед запуском необходимо указать пути к файлам модели и токенизатора в блоке `if __name__ == "__main__":`. Для выхода используйте `Ctrl+C`.

```bash
python onnx_use.py
```

---

**`onnx_local_use.py`** - десктопное GUI-приложение на базе PyQt5. Модели загружаются из zip-архивов, расположенных в той же директории, что и скрипт. Каждый архив должен содержать файлы `encoder.onnx`, `decoder.onnx` и директорию `tokenizer/`. Архивы с именами вида `ru-en.zip` или `ru-en-large.zip` автоматически получают читаемые названия (`RU -> EN`, `RU -> EN Large`) в выпадающем списке. Перевод выполняется автоматически через 300 мс после окончания ввода.

```bash
python onnx_local_use.py
```

---

**`model_dist_server.py`** - FastAPI-сервер для раздачи ONNX-моделей мобильному приложению. Сканирует директорию с zip-архивами и предоставляет REST API для получения их списка и скачивания. Директория с архивами задаётся переменной среды `MODELS_DIR` (по умолчанию `./onnx_export/models`). После запуска сервер доступен по адресу `http://0.0.0.0:9100`(пример можно увидеть, перейдя по ссылке [http://igorpet.ru:9100](http://igorpet.ru:9100)).

```bash
python model_dist_server.py
```

| Метод | Путь                 | Описание                     |
| ----- | -------------------- | ---------------------------- |
| GET   | `/models`            | Список доступных моделей     |
| GET   | `/models/{filename}` | Скачать zip-архив модели     |
| GET   | `/ping`              | Проверка доступности сервера |

### 4.8 Системные требования и производительность

Минимальные системные требования для запуска готовой модели: 1 ГБ свободной оперативной памяти и два процессорных ядра. Благодаря столь низким требованиям к ресурсам переводчик можно использовать практически на любом устройстве для разных задач — от личного использования на старых мобильных телефонах и ноутбуках до массовых переводов на современных серверах.

Ниже приведены результаты замеров скорости генерации на различных устройствах (средняя модель, со слоями FeedForward, сжатыми до точности INT8, CPU):

| Телефон (эмулятор Android Studio, 2 ГБ ОЗУ, 2 ядра) | до 8,5                | до 30                  |

### 4.9 Сравнение с аналогами

Ключевое отличие "Полиглота" от аналогов — полная открытость пайплайнов. Большинство существующих решений (Helsinki-NLP, NLLB-200, Google Translate, DeepL, Яндекс Переводчик) предоставляют либо только готовые веса, либо закрытый API. Polyglot покрывает весь цикл: предобработку данных, обучение, серверный и мобильный инференс — каждый этап задокументирован и доступен для модификации. Любой желающий может обучить собственную языковую пару, изменить архитектуру или адаптировать модель под конкретную задачу.

В отличие от большинства open-source аналогов, проект использует современную архитектуру трансформера и будет поддерживаться в актуальном состоянии по мере появления новых архитектурных решений.

## 5. Выводы

В ходе выполнения проекта была разработана и обучена компактная нейросеть для машинного перевода с русского языка на английский и обратно, ориентированная на запуск в условиях ограниченных вычислительных ресурсов.

| Поставленная задача                   | Результат                                                                                                                                                                                                                                                                                                    |
| ------------------------------------- |--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Размер модели не более 1,5 ГБ         | Выполнено: модель в формате INT8 укладывается в ограничение: малая модель весит ~480 мегабайт, сейчас в процессе обучения средняя модель ~690 мегабайт, в дальнейшем планируется создание большой модели для использования на производительных устройствах ~1.5 гигабайта.                                   |
| Сохранение смысла перевода            | Частично выполнено: хотя модель уже успешно справляется с заметным количеством задач, текущая модель отстаёт от коммерческих аналогов.                                                                                                                                                                       |
| Сравнимость с коммерческими сервисами | Выполнено: Были созданы все варианты инференса, которые обычно есть у коммерческих решений, а так же некоторые другие примеры.                                                                                                                                                                               |

Принятая парадигма «одни веса - одна языковая пара» подтвердила свою эффективность: специализированная модель стабильно превосходит универсальные многоязычные аналоги сопоставимого размера на целевой языковой паре.

Квантование до точности INT8 позволило существенно сократить объём занимаемой памяти и количество вычислений без заметных потерь в точности предсказаний, что подтверждает пригодность данного подхода для развёртывания на мобильных устройствах.

Таким образом, все ключевые цели проекта достигнуты: создан обширный инструментарий для разработки и инференса моделей перевода.

## 6. Направления дальнейшего развития проекта

### 6.1 Поддержка новых языковых пар

В настоящее время модель обучена исключительно для перевода с русского языка на английский и обратно. В перспективе планируется реализация модульности, предусматривающей совместимость энкодеров и декодеров различных языковых пар между собой. Например, при наличии двух предварительно обученных моделей (русский–английский и французский–немецкий) из их компонентов возможно формирование моделей для перевода с русского на немецкий и с французского на английский.
Помимо этого для повышения заинтересованности рядовых потребителей в сервисе приложения, планируется наращивать вычислительные мощности для быстрого расширения перечня моделей перевода разных языков. Это позволит проекту быть более конкурентоспособным. 

---

### 6.2 Улучшение качества перевода

Несмотря на удовлетворительные результаты, определён ряд направлений для повышения качества перевода:

- фильтрация имеющихся наборов данных по качеству перевода;
- тонкая настройка (fine-tuning) на специализированных доменах - юридическом, медицинском, техническом и пр.;
- обучение с подкреплением на основе человеческой обратной связи (RLHF) для повышения естественности переводов;
- расширение тренировочного корпуса за счёт дополнительных открытых параллельных датасетов.

---

### 6.3 Развитие пользовательских интерфейсов

- публикация полноценного Python-модуля для упрощения интеграции моделей в сторонние проекты в качестве библиотеки;
- реализация REST API-сервера для встраивания переводчика в веб-приложения и сервисы.
