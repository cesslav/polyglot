## 1. Введение

Тема этого проекта — «Разработка и обучение нейросети под задачи машинного перевода для запуска на мобильных устройствах».

Актуальность проекта обусловлена отсутствием доступного бесплатного инструмента машинного перевода, пригодного как для массовой обработки текстов в рамках сторонних разработок, так и для индивидуального использования.

Продуктом проекта является готовая модель нейросети для перевода с русского языка на английский, а также репозиторий с открытой лицензией, содержащий полный исходный код проекта. Репозиторий предоставляет возможность любому пользователю воспроизвести переводчик для произвольной языковой пары или адаптировать проект под собственные нужды.

---

## 2. Постановка задачи

### 2.1 Формализация

Главной задачей проекта являлась разработка и обучение модели нейросети для перевода с одного естественного языка на другой, сочетающей компактность, достаточную для запуска на устройствах с минимальными вычислительными ресурсами, и качество перевода, обеспечивающее сохранение смысла исходного текста.

### 2.2 Выбор языков

В качестве демонстрационной языковой пары выбран перевод с русского языка на английский. Данный выбор обусловлен возможностью непосредственного контроля качества получаемых переводов.

### 2.3 Требования

С целью обеспечения широкой доступности модели были установлены жёсткие ограничения на потребление вычислительных ресурсов и, соответственно, на размер модели. По результатам небольшого исследования установлено, что значительная часть пользователей эксплуатирует устройства с тремя гигабайтами оперативной памяти. Данный показатель принят за ориентир. Поскольку часть ресурсов устройства занята операционной системой и иными приложениями, предельный объём памяти, занимаемой моделью, установлен в 1,5 гигабайта. Ввиду сложности формализации требований к качеству перевода проводилось сравнение разработанного переводчика с решениями ведущих участников рынка: Яндекс, Google и DeepL.

## 3. Программные решения

### 3.1 Архитектура

На начальном этапе проекта в качестве базовой архитектуры рассматривалась полносвязная нейросеть (перcептрон), однако данный подход был признан неэффективным для решения поставленной задачи. По результатам исследования альтернативных архитектур была выбрана архитектура трансформера. Реализованная модель имеет концептуальное сходство с семейством моделей Google T5, однако включает ряд модификаций: функция активации ReLU заменена на GeLU, механизм позиционного кодирования существенно переработан, механизм внимания оптимизирован. В остальном модель представляет собой стандартный трансформер со стандартным механизмом позиционного кодирования и стандартным многоголовым механизмом внимания.

### 3.2 Обучение

В качестве парадигмы принят подход «одни веса — одна языковая пара». Данное решение принято с целью устранения недостатков многоязычных моделей, обобщающая способность которых распределяется между множеством языков, что снижает качество обработки каждого из них. Специализированная модель, ориентированная на одну языковую пару, обеспечивает более высокое качество перевода в рамках этой пары при прочих равных.

### 3.3 Оценка качества

Оценка качества перевода является одним из наиболее сложных аспектов проекта. В идеальных условиях она предполагает привлечение экспертов, владеющих обоими языками, однако данный подход сопряжён со значительными ресурсными затратами. Первоначально рассматривалась возможность обучения по принципу GAN - с параллельным обучением двух моделей: одной для перевода и другой для оценки близости перевода к оригиналу по смыслу. Данный метод был отклонён как малоэффективный применительно к обработке естественных языков. В итоге принят более распространённый подход: на этапе обучения в качестве функции потерь используется вероятность, которую модель присваивает ожидаемому следующему фрагменту текста; при ручной оценке результатов обучения принимаются во внимание предсказания модели, субъективное мнение тестеров, а также близость предсказаний к переводам коммерческих сервисов.

### 3.4 Данные для обучения

В процессе разработки использовались следующие наборы данных:

| Набор данных                     | Примечание                                                      |
| -------------------------------- | --------------------------------------------------------------- |
| `wmt/wmt19`                      | —                                                               |
| `ymoslem/Tatoeba-Translations`   | —                                                               |
| `HuggingFaceFW/finetranslations` | Не использовался при обучении итоговой модели;                  |
| `openlanguagedata/flores_plus`   | Был использован только для валидации, в обучении не участвовал. |

Перед использованием содержимое наборов данных было отфильтровано по длине и токенизировано. Иных изменений не вносилось.

## 4. Использование материалов проекта

### 4.1 Обучение токенизатора

Для обучения токенизатора необходимо запустить файл `tok_learn.py`. По завершении выполнения будет создана директория `tokenizer/` с файлами токенизатора.

```bash
python tok_learn.py
```

### 4.2 Предобработка наборов данных

Для предварительной обработки данных необходимо запустить файл `pre_tokenize.py`. Для запуска требуется обученный токенизатор (см. [п. 4.1](#41-обучение-токенизатора)); его главную директорию следует поместить в одну директорию с программой. По завершении выполнения будет создана директория `sources/` с двумя вложенными директориями: `s512_full/` и `s512_val/`, содержащими файлы сохранений обработанных тренировочного и валидационного датасетов соответственно.

```bash
python pre_tokenize.py
```

> **ВНИМАНИЕ!** Временные файлы, создаваемые данной программой, могут занимать значительный объём постоянной памяти.

### 4.3 Обучение модели переводчика

Для обучения переводчика необходимо запустить файл `train.py`. Для запуска требуются тренировочный и валидационный наборы данных (см. [п. 4.2](#42-предобработка-наборов-данных)), файл с реализацией модели `imp.py`, а также конфигурационный файл `train_config.txt`. Директории наборов данных могут располагаться произвольно при условии указания соответствующих путей в конфигурационном файле; файлы с реализацией и с конфигурацией должны находиться в одной директории с программой. По завершении выполнения в директории для сохранения контрольных точек будут созданы файлы контрольных точек с обученными весами (расширение `.pt`).

```bash
python train.py
```

### 4.4 Тестирование обученных весов

Для тестирования обученных весов необходимо запустить файл `use.py`. Для запуска требуются обученные веса из сохранённой контрольной точки (см. [п. 4.3](#43-обучение-модели-переводчика)), обученный токенизатор (см. [п. 4.1](#41-обучение-токенизатора)) и файл с реализацией модели `imp.py`. Главную директорию токенизатора следует поместить в одну директорию с программой. Файл контрольной точки необходимо переименовать в `transformer.pt` и поместить в ту же директорию, туда же следует поместить файл `imp.py`. Программа принимает текст для перевода через консольный интерфейс и выводит предсказания модели декодированные в текст.

```bash
python use.py
```

### 4.5 Преобразование файла сохранения в готовую модель

Для преобразования контрольной точки в модель, готовую к повседневному использованию и распространению, необходимо запустить файл `onnx_export.py`. Для запуска требуется контрольная точка с обученными весами (см. [п. 4.3](#43-обучение-модели-переводчика)); её файл следует переименовать в `transformer.pt` и поместить в директорию с программой. По завершении выполнения будет создана директория `onnx_export/`, содержащая четыре файла:

|Файл|Описание|
|---|---|
|`encoder_fp32.onnx`|Стандартная точность (FP32)|
|`decoder_fp32.onnx`|Стандартная точность (FP32)|
|`encoder_fp8.onnx`|Повышенная степень сжатия (FP8)|
|`decoder_fp8.onnx`|Повышенная степень сжатия (FP8)|

Файлы `encoder_fp32.onnx` и `decoder_fp32.onnx` являются функциональными эквивалентами файлов `encoder_fp8.onnx` и `decoder_fp8.onnx` соответственно. Файлы в формате FP8 обеспечивают более высокую степень сжатия, что снижает потребление ресурсов устройства при работе модели; при этом возможно незначительное снижение точности предсказаний (в рамках обученных мной моделей данный эффект не проявился). Каждая из пар файлов представляет собой одну модель.

```bash
python onnx_export.py
```

### 4.6 Использование готовой модели

Готовая модель допускает интеграцию в любые программные решения. Для демонстрации подготовлен ряд программ:

| Файл          | Интерфейс    | Примечание                                                     |
| ------------- | ------------ | -------------------------------------------------------------- |
| `web.py`      | Веб-сайт     | -                                                              |
| `telegram.py` | Telegram-бот | Для работы дополнительно требует токен API Телеграмма для бота |
| `onnx_use.py` | Консоль      | В процессе разработки                                          |

Каждая из перечисленных программ требует наличия обученного токенизатора (см. [п. 4.1](#41-обучение-токенизатора)) и готовой модели (см. [п. 4.5](#45-преобразование-файла-сохранения-в-готовую-модель)). Главную директорию токенизатора следует поместить в одну директорию с соответствующей программой. Файлы готовой модели необходимо переименовать, удалив суффикс после нижней черты (включительно) вплоть до расширения файла, например:

```
encoder_fp32.onnx  ->  encoder.onnx
decoder_fp8.onnx   ->  decoder.onnx
```

После запуска программы переводчик доступен через соответствующий интерфейс: веб-сайт для `web.py`, чат с Telegram-ботом для `telegram.py`, консольный интерфейс для `onnx_use.py`.

## 5. Выводы

В ходе выполнения проекта была разработана и обучена компактная нейросеть для машинного перевода с русского языка на английский, ориентированная на запуск в условиях ограниченных вычислительных ресурсов.

| Поставленная задача                   | Результат                                                                                                                           |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Размер модели не более 1,5 ГБ         | Выполнено: модель в формате FP8 укладывается в ограничение: меньшая модель весит примерно 690 мегабайт, а средняя - 950 мегабайт.   |
| Сохранение смысла перевода            | Выполнено: модель корректно перевела все тестовые запросы.                                                                          |
| Сравнимость с коммерческими сервисами | Частично выполнено: модель демонстрирует приемлемые результаты, однако по качеству перевода всё ещё уступает коммерческим сервисам. |
| Открытый исходный код                 | Выполнено: репозиторий опубликован на платформе [Github](https://github.com/cesslav/polyglot) под открытой лицензией AGPLv3.        |

Принятая парадигма «одни веса — одна языковая пара» подтвердила свою эффективность: специализированная модель стабильно превосходит универсальные многоязычные аналоги сопоставимого размера на целевой языковой паре.

Квантование до формата FP8 позволило существенно сократить объём занимаемой памяти без заметных потерь в точности предсказаний, что подтверждает пригодность данного подхода для развёртывания на мобильных устройствах.

Таким образом, все ключевые цели проекта достигнуты: создана работоспособная, открытая и воспроизводимая система машинного перевода, доступная как конечным пользователям, так и разработчикам.

## 6. Направления дальнейшего развития проекта

### 6.1 Поддержка новых языковых пар

В настоящее время модель обучена исключительно для перевода с русского языка на английский. В перспективе планируется реализация модульности, предусматривающей совместимость энкодеров и декодеров различных языковых пар между собой. Например, при наличии двух предварительно обученных моделей (русский–английский и французский–немецкий) из их компонентов возможно формирование моделей для перевода с русского на немецкий и с французского на английский.

### 6.2 Улучшение качества перевода

Несмотря на удовлетворительные результаты, определён ряд направлений для повышения качества перевода:

- фильтрация имеющихся наборов данных по качеству перевода;
- тонкая настройка (fine-tuning) на специализированных доменах — юридическом, медицинском, техническом и пр.;
- обучение с подкреплением на основе человеческой обратной связи (RLHF) для повышения естественности переводов;
- расширение тренировочного корпуса за счёт дополнительных открытых параллельных датасетов.

### 6.3 Развитие пользовательских интерфейсов

- публикация полноценного Python-модуля для упрощения интеграции моделей в сторонние проекты в качестве библиотеки;
- реализация REST API-сервера для встраивания переводчика в веб-приложения и сервисы.
